## Features implemented

- **Descriptions** — each task can have a description, edited from a detail modal opened by clicking the task row; when set, it shows as a single truncated line (with an ellipsis if it overflows) beneath the task. Supports a small hand-rolled markdown subset — **bold**, *italic*, `code`, [links](url), and `-`/numbered lists — rendered as real React elements rather than parsed HTML, so there's no `dangerouslySetInnerHTML`/sanitization surface at all. The detail modal shows a live "Preview" box below the textarea as you type; the row's truncated one-line summary renders the same inline formatting (bold/italic/code/links) without the block-level list/paragraph structure, since that wouldn't make sense clamped to one line.
- **Attachments/links** — a task can have multiple attachments (own `attachments` table, one-to-many), added via an "Add attachment…" button in the detail modal that opens a native multi-select file picker (`@tauri-apps/plugin-dialog`). Image attachments (png/jpg/jpeg/gif/webp/svg/bmp) render as inline thumbnail previews right there in the modal (via `convertFileSrc` + the Tauri asset protocol) and enlarge into a full-size in-app lightbox on click; anything else shows as a filename link that opens the file in its default application (`@tauri-apps/plugin-opener`'s `openPath`, with errors surfaced via an alert instead of failing silently) without leaving the app. Each attachment has its own remove button. The task row shows a 📎 badge (with a count once there's more than one) listing the filenames in its tooltip.
- **Edit task title** — the same detail modal has the title as an editable field directly (no separate edit button/mode) alongside due date and description.
- **Due dates** — a date picker in the Add Task modal and the detail modal; due dates show as a badge on each task row. An optional time picker sits next to it (disabled until a date is set, and cleared automatically if the date is), and a set time shows right alongside the date in the badge, e.g. `2026-08-01 14:30`. Overdue detection now accounts for the time too — a task due today at a specific time only flips to overdue once that time has actually passed, instead of the whole day counting as overdue from midnight.
- **Today view** — filters tasks due today, shows a completed/total progress bar, and nests matching subtasks under their parent the same way the All view does.
- **Overdue handling** — incomplete tasks whose due date has passed get a distinct visual state everywhere they appear (a red left-border accent down the whole task block, plus a bolded, red-tinted due-date badge with a warning icon), not just a plain badge. The Today view also gets a dedicated "Overdue" section above the day's list, so a missed task doesn't just silently disappear once its due date passes (it wouldn't otherwise show in Today, which only matches `dueDate === today`).
- **Desktop notifications** — a native OS notification fires the moment an incomplete task becomes overdue (via `@tauri-apps/plugin-notification`), reusing the exact same due/overdue check the rest of the app already relies on — for a task with a specific time that's the instant that time passes, otherwise it's midnight on the due date. Permission is requested once on startup if not already granted. Rather than a one-shot alert, an overdue task keeps re-notifying on a repeat interval for as long as it stays overdue and incomplete — effectively an automatic snooze; a small 🔔 icon in the header lets you pick that interval (15 min – 4 hours, default 1 hour), persisted across restarts. A task's snooze clock is tracked per-task and resets the moment it's no longer overdue (completed, or its due date/time pushed later), so it notifies on a fresh clock if it becomes overdue again later. A background check runs every 60 seconds (plus once immediately) so a task that's due later today still gets caught without the app needing to reload. The same 🔔 popover has a "Do Not Disturb" checkbox (the icon itself switches to 🔕 while it's on) that pauses the check entirely — not just skipping the notification, but the snooze-clock bookkeeping too, so time spent with it on doesn't count against the interval. Turning DND back off re-evaluates on the very next tick as if no time had passed while paused, rather than picking up a stale countdown or staying silent for up to another full interval.
- **This Week view** — filters tasks due within the current week (matching the Calendar view's week layout — see "Configurable week start" below for which day that week begins on), shows the same completed/total progress bar as the Today view, and nests matching subtasks the same way the other filtered views do.
- **No-due-date view** — filters tasks with no due date set, nesting matching subtasks under their parent the same way the All view does.
- **Subtasks** — unlimited nesting via a self-referencing `parent_id`, rendered recursively with inline "+ Subtask" add and cascading delete; a new subtask inherits its parent's due date; ticking a task also ticks all of its subtasks; tasks with subtasks can be collapsed/expanded via a caret toggle. The inline add-subtask form has its own ✕ button (and Escape) to back out, and closes itself automatically if you click away while it's still empty, so an unused form never lingers. A task with subtasks also shows a small "`<completed>/<total>`" badge next to its title, counting its *entire* subtree (nested sub-subtasks included, not just direct children) so overall progress is visible at a glance even while collapsed.
- **Task dependencies** — a "Depends on" section in the task detail modal lets a task require one or more other tasks to finish first, via a new `task_dependencies` table (independent of the `parent_id` subtask hierarchy — a dependency can be any other task, not just a sibling/parent). A blocked task's checkbox is disabled everywhere it's shown, with a 🔒 badge listing what it's waiting on; that guard is enforced twice — once in the disabled checkbox itself, and again at the shared completion code both single-toggle and bulk-complete route through, so bulk-complete can't silently complete a blocked task by bypassing the checkbox. Adding a dependency is rejected (with an explanation) if it would create a direct or transitive cycle — two or more tasks depending on each other in a loop would leave every task in that loop permanently uncompletable, so it's checked for before the edge is ever written.
- **Calendar view** — a larger month grid (the app widens to fit it) with taller day cells that fill in real leading/trailing days from adjacent months instead of blank cells. Each task due that day renders as its own horizontal color-coded strip (by its first tag's color, falling back to its priority color, then a neutral gray) with a line-through/dimmed style once completed, instead of a single dot; a subtask due the same day as its parent is left out of the strip list since the parent's strip already covers it (it still appears in full below). Day navigation and the detail section listing the selected day's full task tree are unchanged; clicking a day still sets that date on the add-task form. A recurring task only ever has one real row in the database (its next upcoming instance — completing it clears that row's recurrence and spawns the next), so the grid also projects the rest of that series forward across the visible month as dashed "⟳" ghost strips, and the day-detail section lists them under an "Upcoming repeats" heading when you select one of those days. These projected occurrences are read-only previews, not real tasks yet, so they can't be completed or deleted from the calendar.
- **Configurable week start** — a Sun/Mon dropdown in the header (persisted in `localStorage`) controls which day the week begins on for both the Calendar grid and the This Week view, previously hardcoded to Sunday in both. `getWeekRange()` and the Calendar's month-grid padding math were generalized from a Sunday-specific offset to a parameterized one; the weekday header row (Sun/Mon/Tue/…) reorders to match instead of just relabeling in place.
- **Recurring tasks** — daily/weekly/monthly/yearly repeat rules with an optional end date **and/or** a cap on how many times the series repeats; completing a recurring task generates its next instance automatically. Whichever bound the series hits first stops it: the end-date check and the occurrence-count check are independent and both apply if both are set. The occurrence cap is stored as `occurrences_remaining` on the shared `recurrence_rules` row — it means "how many occurrences remain, including the current pending one," so it's decremented by one (via `decrementRecurrenceOccurrences`) every time the series advances, whether that's a normal completion spawning the next instance or a "Skip". A weekly rule can also repeat on specific days of the week (e.g. "every Mon/Wed/Fri") instead of the plain every-N-weeks interval — the two modes are mutually exclusive (picking any weekday hides the "every N week(s)" input, since combining them would be more confusing than useful), and `nextRecurrenceDate()` is the one place that decides which mode applies so every call site that needs to advance a series (completing, skipping, projecting future occurrences on the calendar) goes through the same logic rather than each re-deciding it. The repeat rule (frequency/interval/end date/occurrence cap/weekdays) is fully visible and editable from the task detail modal too (same controls as the add form) — turning it on for the first time creates a new recurrence rule and attaches it, changing any of its fields on an existing one updates that rule in place, and switching back to "Doesn't repeat" clears it from the task. A "Skip" button appears on any recurring task's row — it advances that task's own due date to the next occurrence in place (same rule, same row) without marking it complete or leaving a completion record behind, so one occurrence can be skipped without disturbing the rest of the series. If skipping (or completing) would exceed the end date or exhaust the occurrence cap, there's nothing left to advance to, so the recurrence is dropped instead. Non-recurring tasks get the equivalent "Postpone" button instead (shown whenever a task has a due date but no repeat rule) — it just pushes that due date forward by a day in place, for the common "not today, try again tomorrow" case without opening the detail modal to change the date by hand. Both the Add Task modal and the detail modal also show a live "Next: `<date>` `<date>` …" preview of up to 5 upcoming occurrences while a repeat rule is being set up, computed off the due date currently entered via a new `previewOccurrences()` helper — the same interval/weekday/end-date/occurrence-cap logic `nextRecurrenceDate()` and the Calendar view's ghost-occurrence projection already use, just run against an in-progress rule instead of one already saved to a `recurrence_rules` row. It reads "No further occurrences — this would be the only one" if the occurrence cap or end date leaves nothing beyond the due date itself, and prompts for a due date first if none is set yet, since the preview has nothing to anchor off otherwise.
- **Light/dark mode** — a toggle in the header that persists the choice and falls back to the OS theme preference. A small colored-dot button next to it opens a custom accent color picker (a native `<input type="color">`) that overrides `--color-accent`/`--color-accent-soft` as inline styles on the root element — inline styles win over `index.css`'s `:root`/`[data-theme]` rules regardless of which theme is active, so one custom color applies across both light and dark mode. The "soft" tint used for active/selected states is derived automatically from the picked color (an alpha-blended `rgba()`, not a second color to pick), persisted in `localStorage`, and "Reset to theme default" just removes the inline overrides so the stylesheet's normal per-theme accent takes back over.
- **Today view defaults** — the Add Task modal's due date defaults to today whenever the Today view is selected.
- **Tags** — user-created, color-coded labels (name + color picker) assigned to tasks from the detail modal; a task can have multiple. New tags default to a random color not already in use (from a curated palette, falling back to fully random once the palette's exhausted) so you don't have to manually pick one unless you want to. An "Edit tags" link next to the tag filter row opens a management modal to rename, recolor, or delete any tag. Tag chips show on their own wrapping row beneath each task (so a task with many tags doesn't push its title, due date, or buttons out of the row), and a tag filter row lets you narrow any view (including Calendar) down to tasks carrying a chosen tag.
- **Tag inheritance** — subtasks are considered tagged with anything any ancestor carries, computed at query time via a recursive CTE (not copied onto the subtask), so untagging a parent instantly stops all descendants from matching that tag. Inherited tag chips render outlined/muted to distinguish them from a task's own direct (filled) tags, and the tag filter still nests a matching subtask under its real parent.
- **Priority levels** — tasks can be set to low/medium/high priority (color-coded pickers in both the Add Task modal and detail modal), shown as a small colored flag next to the title. A priority filter row (High/Medium/Low chips) narrows any view down to only tasks flagged with the selected priority plus their full subtree of subtasks — everything else, including unprioritized tasks, is hidden rather than just reordered. A matching task's subtasks start collapsed if they aren't all the same priority, so the flagged task doesn't get buried under non-matching clutter. The filter row is explicitly labeled "Filter by priority:" with pill-shaped chips so it doesn't get confused with a picker for setting a task's own priority.
- **Pinning** — a ☆/★ toggle next to every task's checkbox pins it to a small "★ Pinned" shortlist that sits above the view tabs, visible no matter which view, tag/priority filter, or search is currently active — it's a deliberately independent "glance list," not one more thing subject to whatever the current filter context happens to be. Pinning is completely separate from priority; a task can be both, neither, or either independently.
- **In-progress status** — a ○/◐ toggle next to the pin star lets an incomplete task be marked "in progress" (new `in_progress` column on `tasks`), giving a tri-state status — not started / in progress / done — beyond the plain complete/incomplete checkbox. `completed` stays the single source of truth for "done" and everything built on it (dependencies, recurrence, notifications, History/Archive, streaks) is completely untouched by this; `in_progress` only distinguishes the two flavors of "not done yet," toggled independently of completing a task. The toggle only shows while a task is incomplete — completing it makes the distinction moot — and un-completing a task afterward brings back whatever in-progress state it had before, rather than resetting it.
- **Per-task time log** — a ▶/⏸ start/stop timer on any incomplete task's row (new `time_spent_seconds`/`timer_started_at` columns on `tasks`) with the running total shown right next to it (`0:00`/`12:34`/`1:02:34`, `formatDuration()` in `lib/duration.ts`). Elapsed time is computed purely from wall-clock time — `timer_started_at` is a precise ISO timestamp, and the live display is `time_spent_seconds + (Date.now() - that timestamp)` recomputed fresh every second via a per-row `setInterval` — so it stays correct across the app being closed and reopened mid-timer rather than depending on the app having been running the whole time. Stopping (or completing the task, which stops it automatically so a timer doesn't keep silently accumulating in the background after you're done) folds the elapsed run into the total and clears `timer_started_at`; starting again later just adds another run on top. Only one row's timer ticks its own display — no app-wide re-render loop — since the interval lives in `TaskRow` itself, scoped to whichever specific tasks currently have one running. Starting a timer also marks the task "in progress" (if it isn't already) — starting work on something is a reasonable moment to say so — but this is one-directional: stopping the timer leaves the in-progress flag alone, since a paused timer (a break, done for the day) doesn't mean the task itself is no longer in progress, and marking something "in progress" by hand never auto-starts its timer either.
- **History view** — a new `completed_at` column records the local date and 24-hour time a task was finished, e.g. `2026-07-11 21:34` (set/cleared alongside the existing `completed` flag). The History tab groups completed tasks into day sections (most recent first, grouped by the date portion of the timestamp) and each nests subtasks the same way every other view does; tasks completed before this feature existed (no recorded timestamp) land in a trailing "Unknown date" group instead of disappearing. Each row also shows a "Completed `<date> <time>`" badge, and the checkbox is disabled here — History is a read-only record, so you can't accidentally un-complete something by clicking it (deleting or editing a task from this view still works).
- **Archive view** — a new `archived` boolean column on `tasks` lets an already-completed task be moved out of the everyday working set entirely — including out of History, not just visually hidden — via an "Archive" button that appears on any completed task's row (everywhere a row is shown: main list, Overdue, Pinned shortlist, Calendar, History). A new "Archive" tab groups archived tasks into day sections by completion date, the same layout History uses, with an "Unarchive" button to bring a task back. `getAllTasks()` now excludes archived rows at the query level (`WHERE tasks.archived = 0`) so the exclusion is consistent everywhere the task list is read from, rather than each view having to remember to filter archived tasks out itself. The active tag/priority/search filters reach Archive the same way they reach every other view (see Search below) — it originally showed the full archived list unconditionally, which meant switching to Archive silently dropped whatever filter you had active elsewhere.
- **Backlog/Someday** — a "Backlog"/"Unbacklog" toggle on every task row (new `backlog` column on `tasks`) hides a not-yet-actionable task from All/Today/This Week without archiving or deleting it, surfaced instead in a new flat "Backlog" tab (no day-grouping, since unlike History/Archive a backlog task has no natural date to group by). Unlike Archive, `backlog` isn't excluded at the `getAllTasks()` query level — it stays in the normal task list and is only filtered out client-side from those three specific views, so Calendar (if it has a due date) and History (if it's completed) still show it same as always; "someday, but it has a date" isn't treated as a contradiction. It's also excluded from the overdue-notification loop specifically (not from standalone reminders, which are a separate explicit nudge) — nagging about an overdue task you deliberately hid from Today would undermine the whole point of backlogging it. The Pinned shortlist is unaffected either way, consistent with it already being independent of every other filter.
- **Standalone reminders** — a "Reminder" date/time pair in the task detail modal (new `reminder_at`/`reminder_notified` columns on `tasks`), completely independent of the due date above it: it's a plain nudge, not a due-date stand-in, so it never affects overdue styling or the "due" checks elsewhere in the app. Picking a date with no time defaults to 9am rather than forcing an extra pick. A background check (same 60-second interval the overdue notifier already uses) fires a native OS notification the moment `reminder_at` passes for any incomplete task, then marks it `reminder_notified` so it's a one-shot nudge rather than repeating like the overdue snooze loop; editing or clearing the reminder resets that flag so a re-scheduled reminder fires again at its new time. Each task row shows a 🔔 badge with the reminder's date/time, dimmed once it's fired.
- **Stats view** — a new "Stats" tab built entirely off the same `completed_at` data History already uses, so it needed no schema changes. Five at-a-glance cards (current streak, longest streak within the last 12 weeks, completed today, completed this week, total completed ever) sit above two hand-rolled bar charts — daily for the last 30 days, weekly for the last 12 — both sized off the same computed day-by-day completion count map. Streaks work the way most habit trackers do: an empty *today* doesn't break an in-progress streak (the day isn't over yet), but any other empty day does; "longest streak" is bounded to the 12-week window rather than claiming to be all-time. Like History, it reads whatever tag/priority/search filters are currently active.
- **Drag-and-drop reorder (and reparent)** — a new `sort_order` column drives list order (backfilled from existing ids so nothing's order changed on upgrade; new tasks default to the top of their sibling group, matching the previous newest-first behavior). Each task row has a small ⠿ drag handle; dragging it onto another task always inserts it just before that task among its *new* true siblings, renumbering the whole affected sibling group. When the target already shares the dragged task's parent, that's a same-parent reorder exactly as before; when it doesn't, the drop also reparents the dragged task — its `parent_id` is updated to the target's parent, so dropping onto any top-level task promotes a subtask straight to top-level (a top-level task's parent is already `null`). Dropping onto anything inside the dragged task's own subtree is rejected outright, since that would make it its own ancestor — checked via the same `getDescendantIds()` walk the cascading-delete/-complete logic already uses. Reordering always operates on the full sibling set (both the old and new one, for a reparent) rather than whatever a current filter happens to show, so a hidden sibling's position can't get scrambled by a drag made from a filtered view. Required setting `dragDropEnabled: false` on the window in `tauri.conf.json` — Tauri's native window drag-drop handling (for OS file drops) otherwise blocks the webview's own HTML5 drag-and-drop on Windows.
- **Sort options** — a "Sort by:" dropdown (on any list view — not Calendar/History, which have their own ordering) offers Due date, Priority, and Title, on top of the default Manual (drag order). Sorting is display-only — it re-sorts every sibling group in the current tree by the chosen field (tasks with no due date/priority sort last) without touching `sort_order` in the database, so switching back to Manual instantly restores whatever drag order you had. The ⠿ drag handle disappears while a non-manual sort is active, since dragging to reorder wouldn't survive the next re-sort anyway.
- **Keyboard shortcuts** — `n` opens the Add Task modal, `/` focuses the search field, `↑`/`↓` move focus between task rows (any currently rendered row — collapsed subtasks are skipped automatically since they're just not in the DOM), `Enter` opens whichever row has focus (submitting the Add Task modal still works via the browser's native Enter-in-a-form behavior), and `Esc` closes whichever modal is open (Add Task, task detail, or Manage Tags); otherwise, if the search field is focused, the first `Esc` clears it and a second one (or pressing it while already empty) unfocuses it, and the same unfocus fallback applies to anything else that has keyboard focus (e.g. a task row focused via `↑`/`↓`) — so `Esc` always has something to back out of. All of these except `Esc` are suppressed while a modal is open or while typing in any text field, so they never hijack normal typing — `Esc` is the one shortcut that has to keep working *while* a modal is open, since that's how it closes one. A small "i" icon in the header shows the full list in a hover popover. On top of these in-app shortcuts, `Ctrl`/`⌘`+`Shift`+`N` is registered as a true OS-level global shortcut (via `@tauri-apps/plugin-global-shortcut`) that works even when the app isn't focused — it brings the window to the front (unminimizing it first if needed) and opens the Add Task modal, so you can capture a task without alt-tabbing to the app first.
- **Command palette** — `Ctrl`/`⌘`+`K` opens a searchable overlay (closed with `Esc`, same as every other modal) that fuzzy-matches against every task's title — not just whatever the current view/tag/priority/search filter happens to show, since the whole point is jumping straight to something without navigating to wherever it lives first — plus a short static list of common actions (new task, jump to any view, toggle theme, manage tags, export/import, undo/redo). Matching is a lightweight two-tier scheme with no fuzzy-search library: a plain substring match (ranked by how early it starts, same as the Search field) is tried first, and only falls back to subsequence matching — the query's characters found in order but not necessarily contiguous, e.g. "fnrpt" still finds "Finish report" — when nothing contains it as a literal substring; a subsequence match always ranks behind every substring match, since a real substring is the more relevant read of what was typed. `↑`/`↓` move the highlighted result, `Enter` runs it (opening the task's detail modal, or firing the command), and typing anything narrows both lists at once, ranked together into one list capped at 20 results. With no query typed, it shows just the command list, since dumping every task with nothing typed wouldn't be useful.
- **Search** — a text field filters tasks by a case-insensitive substring match against title or description. It composes with everything else (tag filter → priority filter → search → view filter), so it narrows whichever view/filters are already active — including Calendar, History, and Archive — rather than being a separate mode. A matching subtask whose parent doesn't also match gets promoted to a root in the results, same as the other filters. The tag/priority/search chain is a single `filterByTagPriorityAndSearch()` helper applied to both the non-archived and archived task lists, so Archive can't silently drift out of sync with whatever the other views already do with the same filters.
- **Active filter banner** — whenever a tag, priority, or search filter is narrowing the current view, a highlighted "Filtering: …" banner appears right under the view title, listing exactly which ones (as colored pills matching the tag/priority's own color) plus a one-click "Clear all" — added after it turned out a leftover filter from earlier testing was easy to miss (the tag/priority chips further down the page just quietly stay highlighted) and looked like tasks had silently stopped displaying/saving.
- **Export/import** — "Export" (via `@tauri-apps/plugin-dialog`'s native save dialog) writes every raw table (tasks, tags, task_tags, recurrence_rules, attachments, saved_views, custom_tabs — not the app's joined/computed shape) to a JSON file, so a re-import can restore the exact schema state. "Import" is a full **replace**, not a merge: after an explicit confirm (it's destructive and can't be undone), it wipes those tables and reinserts the backup's rows with their original ids intact, so every relationship (parent_id, tags, attachments) still points at the right place afterward. Uses `@tauri-apps/plugin-fs` for the actual file read/write.
- **Export a task as Markdown** — a separate, much smaller "Export .md" button on every task row (everywhere Duplicate/Save-as-template already are, including Archive/Backlog/History/Calendar) saves just that one task — title as an H1, then due date/priority/tags as a bullet list, the description, and its whole subtask subtree as a nested `- [ ]`/`- [x]` checklist — to its own `.md` file, for sharing outside the app rather than restoring into it like the JSON backup above. Deliberately leaves out anything that's internal bookkeeping once it's left the app (pinned/in-progress/backlog/archived flags, reminders, dependencies, attachments' local file paths, highlight color). The subtree lookup spans the non-archived, archived, *and* trashed task lists together (not just the everyday one), so exporting an archived or backlogged task still finds its own children correctly even though they live in a different list.
- **Undo for delete** — deleting a task (or a bulk-selected batch, see below) doesn't touch the database right away: it (and its subtasks) are hidden from every view immediately, and a "`<n> task(s) deleted`" toast with an **Undo** button appears for 5 seconds. Only once that window elapses uncancelled does it actually move to Trash (see below) — not a real `DELETE` anymore, see Trash for why. Undo just cancels the pending timer; deleting again while one delete is already pending commits the first one immediately rather than juggling two undo windows at once.
- **Trash** — a longer-retention safety net *beyond* the 5-second Undo above: once that window elapses, a deleted task now gets a `deleted_at` timestamp (a soft delete) instead of a real `DELETE`, and lands in a new "Trash" tab — day-grouped like Archive/History — where it can be browsed and **Restore**d, or finished off immediately with **Delete forever**. Restoring or trashing a parent cascades to its whole subtree together, mirroring how cascading delete already worked. Anything left in Trash for more than 30 days is purged for good (`purgeExpiredTrash`, a plain string comparison against a date-only cutoff — `deleted_at`'s "date time" format sorts the same as it compares chronologically), checked once whenever the app starts rather than on a running timer, since a local app only needs to catch up on retention when it's actually opened. Trash is deliberately more minimal than Archive — just Restore/Delete forever, no Duplicate/Pin/Save-as-template — since none of those make sense on a task that's about to be purged. An "Empty Trash" button above the list purges everything in Trash immediately (after a `window.confirm`, same as any other irreversible action in the app) rather than waiting out the 30-day retention window — `emptyTrash()` shares its actual row-deletion logic with `purgeExpiredTrash()` (a small `deleteTrashedTaskIds()` helper both call), just without the date-cutoff `WHERE` clause.
- **Undo/redo for edits** — a separate ↶/↷ pair in the header (and `Ctrl`/`⌘`+`Z` / `Ctrl`/`⌘`+`Shift`+`Z`) covers everything the task detail modal's Save button can change at once — title, description, due date/time, priority, repeat rule, reminder, and highlight color — as one combined history entry per Save click, since that's the single action the user actually took. Undoing reverts every one of those fields back to its value from just before that Save; redoing reapplies them. Making a fresh edit after undoing clears whatever was in the redo stack, same as any standard undo/redo. This is deliberately a separate mechanism from Undo for delete above (a pre-commit cancel window) rather than a unified system — the two undo concepts work differently enough (revert-after-commit vs. cancel-before-commit) that combining them would've meant compromising one to fit the other.
- **Per-task highlight color** — a `<input type="color">` picker in the task detail modal (new `highlight_color` column on `tasks`, nullable) tints just that row with a subtle alpha-blended wash of the picked color (via the same `hexToRgba` helper the custom accent picker uses, now shared from `lib/color.ts`), applied everywhere the row renders (main row, its tag strip, its description line). It's a purely personal marker, completely independent of tags and priority — no filtering, grouping, or other logic reads it. "✕" clears it back to no tint.
- **Add Task modal** — the main screen now just has a compact "+ Add task" button (or press `n`) instead of an always-visible form; clicking it opens a modal styled like the task detail view where title, due date/time, priority, and repeat are all entered at once, then closed again — no more permanently-visible priority/repeat controls cluttering every view. "Cancel" (or clicking outside, or closing without submitting) discards the in-progress task entirely rather than partially saving anything. The quick inline "+ Subtask" add on a task row is unchanged by this — it's still the simple title-only field, since a subtask usually just needs a name.
- **Saved views** — a "+ Save current filters" link appears next to the tag/priority filters whenever at least one is active (or a search is typed), prompting for a name and storing that tag + priority + search combo as its own pill in a "Saved views:" row. Clicking a saved view applies its combo in one click (clicking it again clears back to no filters); a small ✕ on each pill deletes it. Deliberately only captures the tag/priority/search refinements, not which top-level view (All/Today/Calendar/etc.) is open, so a saved view is equally useful whether you're checking Today or All. Deleting a tag it references just drops that part of the combo (via `saved_views.tag_id` being nulled out) rather than breaking the saved view entirely.
- **Custom tabs** — a "+ Tab" button next to the built-in All/Today/Calendar/etc. tabs opens a small modal to name a new tab and bind it to a tag (an existing one, or a brand new one created inline right there). Under the hood a custom tab is just a one-click shortcut for "switch to All and filter by this tag" — clicking it sets both at once, and it lights up whenever those two happen to already be true, the same logic saved views use for their own active state. This is what gives the app a "project" tab per tag (e.g. a "Work" tab) without needing a whole separate project concept alongside tags. Each tab has its own ✕ to delete it, and deleting the tag it points at removes the tab too (unlike a saved view, a tab has no meaning without its tag). A small color dot next to the name (new nullable `color` column on `custom_tabs`) opens the same kind of color picker as the app-wide accent below, but scoped to that one tab: while the tab is active, its color overrides `--color-accent`/`--color-accent-soft` in place of the app-wide custom accent, so each project can have its own visual identity instead of everything sharing one accent. Switching away (or to a tab with no color of its own) falls back to the app-wide accent automatically, since the effective accent is just derived from whichever tab is currently active rather than being a separate thing to keep in sync.
- **Bulk select** — a "Select" button (next to "+ Add task", on any list view — not Calendar/History) puts every task row into selection mode with its own checkbox, and shows a small action bar: **Complete**, **Tag** (pick from a small popover to add a tag to every selected task), **Postpone** (a popover asking "by how many days," applied to whichever *selected* tasks are actually overdue — same eligibility as the single-task Postpone button: has a due date, isn't recurring, since Skip is the recurring equivalent — a selected task that doesn't qualify is just silently left alone rather than erroring), and **Delete** (routes through the same Undo-backed pending delete as a single delete, just with a "N tasks deleted" toast instead of one title). Selecting a parent task is enough to act on its whole subtree too — completing or deleting cascades to descendants exactly like it already does for a single task, so there's no need to individually tick subtasks as well.
- **Duplicate task** — a "Duplicate" button on every task row (everywhere a row is shown, including Calendar's day-detail and History) copies its title, description, due date/time, priority, and tags into a new task, along with its *entire* subtask subtree (each descendant re-parented under its own sibling's duplicate, so the copied hierarchy matches the original exactly). The duplicate always starts fresh — not completed, no completion timestamp — and deliberately doesn't carry over recurrence (so the copy and the original don't end up racing to spawn the same "next instance") or attachments (those are just file paths, so "duplicating" one would only point two tasks at the same file rather than making a real copy). It lands as a sibling of the original, positioned immediately next to it rather than jumping to the top of the list.
- **Task templates** — a "Save as template" button on every task row captures its title, priority, tags, and its whole subtask subtree as a static, named blueprint (a `task_templates` table storing that tree as one JSON blob, since — unlike real tasks — a template never needs to be filtered, sorted, or joined against, only read back whole). A "Templates ▾" button next to "+ Add task" lists every saved template; picking one stamps out a brand-new task (and its whole subtask tree, tags included) in one click, using whatever due date is currently pending for the add form — the same default a manually-added task on that view would get. Templates are completely independent of the task they were captured from: editing, retagging, or deleting the original never touches a template already saved from it.
- **Natural language due dates (and times)** — typing a phrase like "tomorrow", "next friday", "in 3 days", or "next week" anywhere in the Add Task modal's title field shows a small "📅 Due `<date>`" hint beneath it; submitting then strips that phrase out of the title and sets the due date to the resolved date automatically (unless a title were *only* that phrase, in which case the text is left alone so the task doesn't end up with a blank title). A bare weekday name (e.g. "friday") means the next occurrence including today itself; "next friday" always skips the nearest one and lands on the following week's. A time phrase alongside a date — "at 3pm", "at 15:30", "noon", "midnight" — is detected and applied too (never on its own, since a time only means something once there's a date to attach it to); a bare hour with no am/pm, like "at 3", guesses pm for 1–7 and am for 8–12/0 since that's the more common casual meaning. This only kicks in while no due date/time has been picked yet — picking either by hand always wins and the hint disappears.
- **"See also" links** — a "See also" section in the task detail modal, right below "Depends on," lets any two tasks be cross-referenced without either one blocking the other's completion — a new `task_related` table, deliberately separate from `task_dependencies`. Unlike a dependency, the link is symmetric: linking A to B always means B is also linked to A, so it's stored as one canonical row per pair (the smaller id always first) rather than two directional rows that could drift out of sync. Each linked task shows as a clickable title (completed ones struck through) that jumps straight to that task's own detail panel, and a ✕ removes just that one link; adding one is the same "pick from a dropdown of every other task, then Add" pattern as "Depends on." Like dependencies, links aren't carried over by Duplicate or Save-as-template.
- **Click-outside-to-close for popovers** — every small anchored popover in the app (Templates ▾, the bulk-select Tag ▾ and Postpone ▾ pickers, a task row's "⋯" kebab menu, and the sidebar's per-tab color picker/notification-settings/accent-color popovers) now closes itself the moment you click anywhere outside it, not just by re-clicking its own toggle button or picking an option. A new shared `useClickOutside()` hook (`lib/useClickOutside.ts`) attaches a single `mousedown` listener to `document` — only while that specific popover is open, so idle popovers cost nothing — and closes it if the click landed outside the wrapper element the hook was given; that wrapper always contains both the toggle button and the panel itself, so clicking the toggle to *open* it is never misread as an "outside" click. The one popover this deliberately excludes is the sidebar's keyboard-shortcuts info panel, since that one already opens/closes on hover rather than a click and has nothing to close on-outside-click *from*.
- **Microsoft To Do-style layout** — the whole app was restructured from one centered column into three panes: a left `Sidebar.tsx` (the built-in views as a vertical list, custom tabs as a "Lists" section below them, and the app's settings/chrome — theme, accent, notifications, week-start, export/import, undo/redo, shortcuts — pinned to the bottom, in place of the old horizontal tab row and header icon cluster), a scrollable main column (unchanged filter/search/saved-views rows, an inline "+ Add a task" bar in place of the old button, and completed top-level tasks now collapsed into a "Completed (`n`)" footer instead of interleaved with incomplete ones), and a right-side `TaskDetailModal` that now slides in as a fixed panel (its own header with a ✕ close button, no dark backdrop) instead of a centered overlay. `TaskRow` was restyled to a two-line layout (title/star/status icons on top, due date/reminder/tags/etc. as a subtitle line below) with the long tail of per-row actions (Skip, Postpone, Duplicate, Archive, Export .md, etc.) consolidated into a "⋯" menu instead of a row of text buttons. This was a pure restructuring — every existing feature/handler kept working exactly as before, just re-homed into the new layout; no new functionality was added.
