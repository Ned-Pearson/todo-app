## Features implemented

- **Descriptions** — each task can have a description, edited from a detail modal opened by clicking the task row; when set, it shows as a single truncated line (with an ellipsis if it overflows) beneath the task. Supports a small hand-rolled markdown subset — **bold**, *italic*, `code`, [links](url), and `-`/numbered lists — rendered as real React elements rather than parsed HTML, so there's no `dangerouslySetInnerHTML`/sanitization surface at all. The detail modal shows a live "Preview" box below the textarea as you type; the row's truncated one-line summary renders the same inline formatting (bold/italic/code/links) without the block-level list/paragraph structure, since that wouldn't make sense clamped to one line.
- **Attachments/links** — a task can have multiple attachments (own `attachments` table, one-to-many), added via an "Add attachment…" button in the detail modal that opens a native multi-select file picker (`@tauri-apps/plugin-dialog`). Image attachments (png/jpg/jpeg/gif/webp/svg/bmp) render as inline thumbnail previews right there in the modal (via `convertFileSrc` + the Tauri asset protocol) and enlarge into a full-size in-app lightbox on click; anything else shows as a filename link that opens the file in its default application (`@tauri-apps/plugin-opener`'s `openPath`, with errors surfaced via an alert instead of failing silently) without leaving the app. Each attachment has its own remove button. The task row shows a 📎 badge (with a count once there's more than one) listing the filenames in its tooltip.
- **Edit task title** — the same detail modal has the title as an editable field directly (no separate edit button/mode) alongside due date and description.
- **Due dates** — a date picker in the Add Task modal and the detail modal; due dates show as a badge on each task row. An optional time picker sits next to it (disabled until a date is set, and cleared automatically if the date is), and a set time shows right alongside the date in the badge, e.g. `2026-08-01 14:30`. Overdue detection now accounts for the time too — a task due today at a specific time only flips to overdue once that time has actually passed, instead of the whole day counting as overdue from midnight.
- **Today view** — filters tasks due today, shows a completed/total progress bar, and nests matching subtasks under their parent the same way the All view does.
- **Overdue handling** — incomplete tasks whose due date has passed get a distinct visual state everywhere they appear (a red left-border accent down the whole task block, plus a bolded, red-tinted due-date badge with a warning icon), not just a plain badge. The Today view also gets a dedicated "Overdue" section above the day's list, so a missed task doesn't just silently disappear once its due date passes (it wouldn't otherwise show in Today, which only matches `dueDate === today`).
- **Desktop notifications** — a native OS notification fires the moment an incomplete task becomes overdue (via `@tauri-apps/plugin-notification`), reusing the exact same due/overdue check the rest of the app already relies on — for a task with a specific time that's the instant that time passes, otherwise it's midnight on the due date. Permission is requested once on startup if not already granted. Rather than a one-shot alert, an overdue task keeps re-notifying on a repeat interval for as long as it stays overdue and incomplete — effectively an automatic snooze; a small 🔔 icon in the header lets you pick that interval (15 min – 4 hours, default 1 hour), persisted across restarts. A task's snooze clock is tracked per-task and resets the moment it's no longer overdue (completed, or its due date/time pushed later), so it notifies on a fresh clock if it becomes overdue again later. A background check runs every 60 seconds (plus once immediately) so a task that's due later today still gets caught without the app needing to reload. The same 🔔 popover has a "Do Not Disturb" checkbox (the icon itself switches to 🔕 while it's on) that pauses the check entirely — not just skipping the notification, but the snooze-clock bookkeeping too, so time spent with it on doesn't count against the interval. Turning DND back off re-evaluates on the very next tick as if no time had passed while paused, rather than picking up a stale countdown or staying silent for up to another full interval.
- **This Week view** — filters tasks due within the current week (matching the Calendar view's week layout — see "Configurable week start" below for which day that week begins on), shows the same completed/total progress bar as the Today view, and nests matching subtasks the same way the other filtered views do.
- **No-due-date view** — filters tasks with no due date set, nesting matching subtasks under their parent the same way the All view does.
- **Subtasks** — unlimited nesting via a self-referencing `parent_id`, rendered recursively with inline "+ Subtask" add and cascading delete; a new subtask inherits its parent's due date; ticking a task also ticks all of its subtasks; tasks with subtasks can be collapsed/expanded via a caret toggle. The inline add-subtask form has its own ✕ button (and Escape) to back out, and closes itself automatically if you click away while it's still empty, so an unused form never lingers. A task with subtasks also shows a small "`<completed>/<total>`" badge next to its title, counting its *entire* subtree (nested sub-subtasks included, not just direct children) so overall progress is visible at a glance even while collapsed. "Expand all"/"Collapse all" links (next to "Sort by:", on the same views) apply that to every task at once — each row's `collapsed` state is still plain local `useState` (not lifted up into shared app state), so a `collapseSignal` prop of `{ collapsed, version }` just seeds it from outside: bumping `version` re-applies `collapsed` to every mounted row (cascading to nested sub-subtasks via the same prop threaded into the recursive child render), while each row's own caret toggle keeps working independently afterward. Bumping a version counter rather than just passing a boolean is what makes two consecutive clicks of the *same* button both take effect, since the boolean alone wouldn't change between them and the effect wouldn't re-run.
- **Task dependencies** — a "Depends on" section in the task detail modal lets a task require one or more other tasks to finish first, via a new `task_dependencies` table (independent of the `parent_id` subtask hierarchy — a dependency can be any other task, not just a sibling/parent). A blocked task's checkbox is disabled everywhere it's shown, with a 🔒 badge listing what it's waiting on; that guard is enforced twice — once in the disabled checkbox itself, and again at the shared completion code both single-toggle and bulk-complete route through, so bulk-complete can't silently complete a blocked task by bypassing the checkbox. Adding a dependency is rejected (with an explanation) if it would create a direct or transitive cycle — two or more tasks depending on each other in a loop would leave every task in that loop permanently uncompletable, so it's checked for before the edge is ever written.
- **Calendar view** — a larger month grid (the app widens to fit it) with taller day cells that fill in real leading/trailing days from adjacent months instead of blank cells. Each task due that day renders as its own horizontal color-coded strip (by its first tag's color, falling back to its priority color, then a neutral gray) with a line-through/dimmed style once completed, instead of a single dot; a subtask due the same day as its parent is left out of the strip list since the parent's strip already covers it (it still appears in full below). Day navigation and the detail section listing the selected day's full task tree are unchanged; clicking a day still sets that date on the add-task form. A recurring task only ever has one real row in the database (its next upcoming instance — completing it clears that row's recurrence and spawns the next), so the grid also projects the rest of that series forward across the visible month as dashed "⟳" ghost strips, and the day-detail section lists them under an "Upcoming repeats" heading when you select one of those days. These projected occurrences are read-only previews, not real tasks yet, so they can't be completed or deleted from the calendar.
- **Configurable week start** — a Sun/Mon dropdown in the header (persisted in `localStorage`) controls which day the week begins on for both the Calendar grid and the This Week view, previously hardcoded to Sunday in both. `getWeekRange()` and the Calendar's month-grid padding math were generalized from a Sunday-specific offset to a parameterized one; the weekday header row (Sun/Mon/Tue/…) reorders to match instead of just relabeling in place.
- **Recurring tasks** — daily/weekly/monthly/yearly repeat rules with an optional end date **and/or** a cap on how many times the series repeats; completing a recurring task generates its next instance automatically. Whichever bound the series hits first stops it: the end-date check and the occurrence-count check are independent and both apply if both are set. The occurrence cap is stored as `occurrences_remaining` on the shared `recurrence_rules` row — it means "how many occurrences remain, including the current pending one," so it's decremented by one (via `decrementRecurrenceOccurrences`) every time the series advances, whether that's a normal completion spawning the next instance or a "Skip". A weekly rule can also repeat on specific days of the week (e.g. "every Mon/Wed/Fri") instead of the plain every-N-weeks interval — the two modes are mutually exclusive (picking any weekday hides the "every N week(s)" input, since combining them would be more confusing than useful), and `nextRecurrenceDate()` is the one place that decides which mode applies so every call site that needs to advance a series (completing, skipping, projecting future occurrences on the calendar) goes through the same logic rather than each re-deciding it. The repeat rule (frequency/interval/end date/occurrence cap/weekdays) is fully visible and editable from the task detail modal too (same controls as the add form) — turning it on for the first time creates a new recurrence rule and attaches it, changing any of its fields on an existing one updates that rule in place, and switching back to "Doesn't repeat" clears it from the task. A "Skip" button appears on any recurring task's row — it advances that task's own due date to the next occurrence in place (same rule, same row) without marking it complete or leaving a completion record behind, so one occurrence can be skipped without disturbing the rest of the series. If skipping (or completing) would exceed the end date or exhaust the occurrence cap, there's nothing left to advance to, so the recurrence is dropped instead. Non-recurring tasks get the equivalent "Postpone" button instead (shown whenever a task has a due date but no repeat rule) — it just pushes that due date forward by a day in place, for the common "not today, try again tomorrow" case without opening the detail modal to change the date by hand. Both the Add Task modal and the detail modal also show a live "Next: `<date>` `<date>` …" preview of up to 5 upcoming occurrences while a repeat rule is being set up, computed off the due date currently entered via a new `previewOccurrences()` helper — the same interval/weekday/end-date/occurrence-cap logic `nextRecurrenceDate()` and the Calendar view's ghost-occurrence projection already use, just run against an in-progress rule instead of one already saved to a `recurrence_rules` row. It reads "No further occurrences — this would be the only one" if the occurrence cap or end date leaves nothing beyond the due date itself, and prompts for a due date first if none is set yet, since the preview has nothing to anchor off otherwise.
- **Light/dark mode** — a toggle in the header that persists the choice and falls back to the OS theme preference. A small colored-dot button next to it opens a custom accent color picker (a native `<input type="color">`) that overrides `--color-accent`/`--color-accent-soft` as inline styles on the root element — inline styles win over `index.css`'s `:root`/`[data-theme]` rules regardless of which theme is active, so one custom color applies across both light and dark mode. The "soft" tint used for active/selected states is derived automatically from the picked color (an alpha-blended `rgba()`, not a second color to pick), persisted in `localStorage`, and "Reset to theme default" just removes the inline overrides so the stylesheet's normal per-theme accent takes back over.
- **Today view defaults** — the Add Task modal's due date defaults to today whenever the Today view is selected.
- **Tags** — user-created, color-coded labels (name + color picker) assigned to tasks from the detail modal; a task can have multiple. New tags default to a random color not already in use (from a curated palette, falling back to fully random once the palette's exhausted) so you don't have to manually pick one unless you want to. An "Edit tags" link next to the tag filter row opens a management modal to rename, recolor, or delete any tag. Tag chips show on their own wrapping row beneath each task (so a task with many tags doesn't push its title, due date, or buttons out of the row), and a tag filter row lets you narrow any view (including Calendar) down to tasks carrying a chosen tag.
- **Tag inheritance** — subtasks are considered tagged with anything any ancestor carries, computed at query time via a recursive CTE (not copied onto the subtask), so untagging a parent instantly stops all descendants from matching that tag. Inherited tag chips render outlined/muted to distinguish them from a task's own direct (filled) tags, and the tag filter still nests a matching subtask under its real parent.
- **Priority levels** — tasks can be set to low/medium/high priority (color-coded pickers in both the Add Task modal and detail modal), shown as a small colored flag next to the title. A priority filter row (High/Medium/Low chips) narrows any view down to only tasks flagged with the selected priority plus their full subtree of subtasks — everything else, including unprioritized tasks, is hidden rather than just reordered. A matching task's subtasks start collapsed if they aren't all the same priority, so the flagged task doesn't get buried under non-matching clutter. The filter row is explicitly labeled "Filter by priority:" with pill-shaped chips so it doesn't get confused with a picker for setting a task's own priority.
- **Pinning** — a ☆/★ toggle next to every task's checkbox pins it to a small "★ Pinned" shortlist that sits above the view tabs, visible no matter which view, tag/priority filter, or search is currently active — it's a deliberately independent "glance list," not one more thing subject to whatever the current filter context happens to be. Pinning is completely separate from priority; a task can be both, neither, or either independently.
- **In-progress status** — a ○/◐ toggle next to the pin star lets an incomplete task be marked "in progress" (new `in_progress` column on `tasks`), giving a tri-state status — not started / in progress / done — beyond the plain complete/incomplete checkbox. `completed` stays the single source of truth for "done" and everything built on it (dependencies, recurrence, notifications, History/Archive, streaks) is completely untouched by this; `in_progress` only distinguishes the two flavors of "not done yet," toggled independently of completing a task. The toggle only shows while a task is incomplete — completing it makes the distinction moot — and un-completing a task afterward brings back whatever in-progress state it had before, rather than resetting it.
- **Per-task time log** — a ▶/⏸ start/stop timer on any incomplete task's row (new `time_spent_seconds`/`timer_started_at` columns on `tasks`) with the running total shown right next to it (`0:00`/`12:34`/`1:02:34`, `formatDuration()` in `lib/duration.ts`). Elapsed time is computed purely from wall-clock time — `timer_started_at` is a precise ISO timestamp, and the live display is `time_spent_seconds + (Date.now() - that timestamp)` recomputed fresh every second via a per-row `setInterval` — so it stays correct across the app being closed and reopened mid-timer rather than depending on the app having been running the whole time. Stopping (or completing the task, which stops it automatically so a timer doesn't keep silently accumulating in the background after you're done) folds the elapsed run into the total and clears `timer_started_at`; starting again later just adds another run on top. Only one row's timer ticks its own display — no app-wide re-render loop — since the interval lives in `TaskRow` itself, scoped to whichever specific tasks currently have one running. Starting a timer also marks the task "in progress" (if it isn't already) — starting work on something is a reasonable moment to say so — but this is one-directional: stopping the timer leaves the in-progress flag alone, since a paused timer (a break, done for the day) doesn't mean the task itself is no longer in progress, and marking something "in progress" by hand never auto-starts its timer either. A "Reset timer" entry in the row's "⋯" menu (only shown once there's actually something to reset — logged time or a run in progress) zeroes `time_spent_seconds` back to 0 and clears `timer_started_at` in one step, guarded by a confirm prompt since the logged total can't be recovered afterward; resetting while a timer happens to be running discards that in-progress run rather than folding it into the total first, since "reset" means a clean slate, not "stop, then zero." A "Time estimate" number input in the task detail modal (new nullable `tasks.estimated_minutes` column, minute granularity — unlike the timer's second precision, nobody estimates to the second) lets you set how long a task is expected to take; once set, the row's timer badge grows a `/ <estimate>` suffix next to the logged total (e.g. `⏱ 12:34 / 30:00`), turning the same red used for overdue due dates once logged time actually exceeds it. The estimate is independent of `time_spent_seconds` — nothing recomputes or clears one when the other changes — so past estimates stay comparable against what a task actually took. Deliberately left out of the Add Task modal, same as reminders — it's a detail-modal-only field, not part of quick capture.
- **History view** — a new `completed_at` column records the local date and 24-hour time a task was finished, e.g. `2026-07-11 21:34` (set/cleared alongside the existing `completed` flag). The History tab groups completed tasks into day sections (most recent first, grouped by the date portion of the timestamp) and each nests subtasks the same way every other view does; tasks completed before this feature existed (no recorded timestamp) land in a trailing "Unknown date" group instead of disappearing. Each row also shows a "Completed `<date> <time>`" badge, and the checkbox is disabled here — History is a read-only record, so you can't accidentally un-complete something by clicking it (deleting or editing a task from this view still works).
- **Archive view** — a new `archived` boolean column on `tasks` lets an already-completed task be moved out of the everyday working set entirely — including out of History, not just visually hidden — via an "Archive" button that appears on any completed task's row (everywhere a row is shown: main list, Overdue, Pinned shortlist, Calendar, History). A new "Archive" tab groups archived tasks into day sections by completion date, the same layout History uses, with an "Unarchive" button to bring a task back. `getAllTasks()` now excludes archived rows at the query level (`WHERE tasks.archived = 0`) so the exclusion is consistent everywhere the task list is read from, rather than each view having to remember to filter archived tasks out itself. The active tag/priority/search filters reach Archive the same way they reach every other view (see Search below) — it originally showed the full archived list unconditionally, which meant switching to Archive silently dropped whatever filter you had active elsewhere.
- **Backlog/Someday** — a "Backlog"/"Unbacklog" toggle on every task row (new `backlog` column on `tasks`) hides a not-yet-actionable task from All/Today/This Week without archiving or deleting it, surfaced instead in a new flat "Backlog" tab (no day-grouping, since unlike History/Archive a backlog task has no natural date to group by). Unlike Archive, `backlog` isn't excluded at the `getAllTasks()` query level — it stays in the normal task list and is only filtered out client-side from those three specific views, so Calendar (if it has a due date) and History (if it's completed) still show it same as always; "someday, but it has a date" isn't treated as a contradiction. It's also excluded from the overdue-notification loop specifically (not from standalone reminders, which are a separate explicit nudge) — nagging about an overdue task you deliberately hid from Today would undermine the whole point of backlogging it. The Pinned shortlist is unaffected either way, consistent with it already being independent of every other filter.
- **Standalone reminders** — a "Reminder" date/time pair in the task detail modal (new `reminder_at`/`reminder_notified` columns on `tasks`), completely independent of the due date above it: it's a plain nudge, not a due-date stand-in, so it never affects overdue styling or the "due" checks elsewhere in the app. Picking a date with no time defaults to 9am rather than forcing an extra pick. A background check (same 60-second interval the overdue notifier already uses) fires a native OS notification the moment `reminder_at` passes for any incomplete task, then marks it `reminder_notified` so it's a one-shot nudge rather than repeating like the overdue snooze loop; editing or clearing the reminder resets that flag so a re-scheduled reminder fires again at its new time. Each task row shows a 🔔 badge with the reminder's date/time, dimmed once it's fired. A "Repeat" dropdown next to it (new nullable `tasks.reminder_repeat` column, reusing the due date's own Daily/Weekly/Monthly/Yearly options) lets the reminder repeat on its own schedule, completely independent of whatever the due date's recurrence is doing (or not doing) — deliberately just a bare frequency rather than the full `recurrence_rules` machinery (no end date/occurrence cap/weekdays), since a standalone nudge doesn't need that much. A repeating reminder never gets marked "already sent": each firing instead rolls `reminder_at` forward to its next occurrence (`nextReminderAfter()` in `lib/date.ts`) and stays pending for the next one, shown with a small ⟳ suffix on the badge. If the app was closed past more than one interval, it jumps straight to the next occurrence still ahead of *now* in one step rather than replaying every missed occurrence as a separate notification on each 60-second check.
- **Stats view** — a new "Stats" tab built entirely off the same `completed_at` data History already uses, so it needed no schema changes. Five at-a-glance cards (current streak, longest streak within the last 12 weeks, completed today, completed this week, total completed ever) sit above two hand-rolled bar charts — daily for the last 30 days, weekly for the last 12 — both sized off the same computed day-by-day completion count map. Streaks work the way most habit trackers do: an empty *today* doesn't break an in-progress streak (the day isn't over yet), but any other empty day does; "longest streak" is bounded to the 12-week window rather than claiming to be all-time. Like History, it reads whatever tag/priority/search filters are currently active. Below the charts, two "Completed by list" / "Completed by tag" breakdowns show a horizontal bar per list/tag (colored to match, an emoji-prefixed label if the list has an icon set) with an all-time completed count — deliberately all-time rather than windowed like the charts above, matching "Total completed." A task counts toward every tag it carries, direct or inherited, same as the tag filter chips elsewhere, so the per-tag total can exceed the per-list/overall one; a trailing "No list"/"Untagged" bar catches everything else. This is a breakdown *within* the existing app-wide Stats page rather than letting Stats itself be opened scoped to one list — selecting a list always forces the view back to "all," so reaching Stats already meant leaving any list context behind.
- **Drag-and-drop reorder (and reparent)** — a new `sort_order` column drives list order (backfilled from existing ids so nothing's order changed on upgrade; new tasks default to the top of their sibling group, matching the previous newest-first behavior). Each task row has a small ⠿ drag handle; dragging it onto another task inserts it just before or just after that task among its *new* true siblings — whichever half of the target row the cursor is currently over decides which (an accent-colored line shows above or below the target to match), renumbering the whole affected sibling group. This is why dropping onto the bottom half of the very last row is the only way to land at the very end of a list: inserting "before" a target can never place something after whatever's currently last, so without a bottom-half "after" option, reaching the last position always meant first moving something else out of the way. When the target already shares the dragged task's parent, that's a same-parent reorder exactly as before; when it doesn't, the drop also reparents the dragged task — its `parent_id` is updated to the target's parent, so dropping onto any top-level task promotes a subtask straight to top-level (a top-level task's parent is already `null`). Dropping onto anything inside the dragged task's own subtree is rejected outright, since that would make it its own ancestor — checked via the same `getDescendantIds()` walk the cascading-delete/-complete logic already uses. Reordering always operates on the full sibling set (both the old and new one, for a reparent) rather than whatever a current filter happens to show, so a hidden sibling's position can't get scrambled by a drag made from a filtered view. Required setting `dragDropEnabled: false` on the window in `tauri.conf.json` — Tauri's native window drag-drop handling (for OS file drops) otherwise blocks the webview's own HTML5 drag-and-drop on Windows.
- **Sort options** — a "Sort by:" dropdown (on any list view — not Calendar/History, which have their own ordering) offers Due date, Priority, and Title, on top of the default Manual (drag order). Sorting is display-only — it re-sorts every sibling group in the current tree by the chosen field (tasks with no due date/priority sort last) without touching `sort_order` in the database, so switching back to Manual instantly restores whatever drag order you had. The ⠿ drag handle disappears while a non-manual sort is active, since dragging to reorder wouldn't survive the next re-sort anyway.
- **Keyboard shortcuts** — `n` opens the Add Task modal, `/` focuses the search field, `↑`/`↓` move focus between task rows (any currently rendered row — collapsed subtasks are skipped automatically since they're just not in the DOM), `Enter` opens whichever row has focus (submitting the Add Task modal still works via the browser's native Enter-in-a-form behavior), `Shift`+`Enter` opens that same focused row's inline "+ Subtask" form instead (same key as plain Enter, held differently, for the related-but-distinct action — the form's own input still autofocuses itself exactly like clicking "+" does), and `Esc` closes whichever modal is open (Add Task, task detail, or Manage Tags); otherwise, if the search field is focused, the first `Esc` clears it and a second one (or pressing it while already empty) unfocuses it, and the same unfocus fallback applies to anything else that has keyboard focus (e.g. a task row focused via `↑`/`↓`) — so `Esc` always has something to back out of. All of these except `Esc` are suppressed while a modal is open or while typing in any text field, so they never hijack normal typing — `Esc` is the one shortcut that has to keep working *while* a modal is open, since that's how it closes one. A small "i" icon in the header shows the full list in a hover popover. On top of these in-app shortcuts, `Ctrl`/`⌘`+`Shift`+`N` is registered as a true OS-level global shortcut (via `@tauri-apps/plugin-global-shortcut`) that works even when the app isn't focused — it brings the window to the front (unminimizing it first if needed) and opens the Add Task modal, so you can capture a task without alt-tabbing to the app first.
- **Command palette** — `Ctrl`/`⌘`+`K` opens a searchable overlay (closed with `Esc`, same as every other modal) that fuzzy-matches against every task's title — not just whatever the current view/tag/priority/search filter happens to show, since the whole point is jumping straight to something without navigating to wherever it lives first — plus a short static list of common actions (new task, jump to any view, toggle theme, manage tags, export/import, undo/redo). Matching is a lightweight two-tier scheme with no fuzzy-search library: a plain substring match (ranked by how early it starts, same as the Search field) is tried first, and only falls back to subsequence matching — the query's characters found in order but not necessarily contiguous, e.g. "fnrpt" still finds "Finish report" — when nothing contains it as a literal substring; a subsequence match always ranks behind every substring match, since a real substring is the more relevant read of what was typed. `↑`/`↓` move the highlighted result, `Enter` runs it (opening the task's detail modal, or firing the command), and typing anything narrows both lists at once, ranked together into one list capped at 20 results. With no query typed, it shows just the command list, since dumping every task with nothing typed wouldn't be useful.
- **Search** — a text field filters tasks by a case-insensitive substring match against title or description. It composes with everything else (tag filter → priority filter → search → view filter), so it narrows whichever view/filters are already active — including Calendar, History, and Archive — rather than being a separate mode. A matching subtask whose parent doesn't also match gets promoted to a root in the results, same as the other filters. The tag/priority/search chain is a single `filterByTagPriorityAndSearch()` helper applied to both the non-archived and archived task lists, so Archive can't silently drift out of sync with whatever the other views already do with the same filters.
- **Active filter banner** — whenever a tag, priority, or search filter is narrowing the current view, a highlighted "Filtering: …" banner appears right under the view title, listing exactly which ones (as colored pills matching the tag/priority's own color) plus a one-click "Clear all" — added after it turned out a leftover filter from earlier testing was easy to miss (the tag/priority chips further down the page just quietly stay highlighted) and looked like tasks had silently stopped displaying/saving.
- **Export/import** — "Export" (via `@tauri-apps/plugin-dialog`'s native save dialog) writes every raw table (tasks, tags, task_tags, recurrence_rules, attachments, saved_views, custom_tabs — not the app's joined/computed shape) to a JSON file, so a re-import can restore the exact schema state. "Import" is a full **replace**, not a merge: after an explicit confirm (it's destructive and can't be undone), it wipes those tables and reinserts the backup's rows with their original ids intact, so every relationship (parent_id, tags, attachments) still points at the right place afterward. Uses `@tauri-apps/plugin-fs` for the actual file read/write.
- **Export a task as Markdown** — a separate, much smaller "Export .md" button on every task row (everywhere Duplicate/Save-as-template already are, including Archive/Backlog/History/Calendar) saves just that one task — title as an H1, then due date/priority/tags as a bullet list, the description, and its whole subtask subtree as a nested `- [ ]`/`- [x]` checklist — to its own `.md` file, for sharing outside the app rather than restoring into it like the JSON backup above. Deliberately leaves out anything that's internal bookkeeping once it's left the app (pinned/in-progress/backlog/archived flags, reminders, dependencies, attachments' local file paths, highlight color). The subtree lookup spans the non-archived, archived, *and* trashed task lists together (not just the everyday one), so exporting an archived or backlogged task still finds its own children correctly even though they live in a different list.
- **Export a whole list as Markdown** — an "Export as Markdown" link in a list's settings popover (next to "Apply to all tasks in this list") saves every task belonging to that list as one combined `.md` checklist, rather than one file per task. It follows the exact same "list membership" rule the app itself uses when the list is open (`filterByTagPriorityAndSearch`'s own listId-plus-descendants walk, duplicated here since that one is scoped to whichever list is currently active rather than whichever list's popover triggered the export): every task whose own `listId` matches, plus their descendants regardless of a descendant's own `listId` — so a subtask that isn't itself assigned to the list still shows up nested under its parent, same as it would browsing the list in-app. A task only ever appears once — as a nested child if its parent is also part of the export, otherwise as its own top-level checklist item — so nothing is duplicated. Due date/priority/tags ride along inline in parens next to each checklist line (e.g. `- [ ] Buy milk (Due: 2026-08-10 · High priority · tags: errands)`) rather than as their own bullet list like the single-task export does, since a multi-task document needs to stay scannable as a checklist; per-task descriptions are left out for the same reason. Shares the same underlying `exportTaskAsMarkdown()` file-save plumbing as the single-task export, just with a new `listToMarkdown()` renderer (`lib/taskMarkdown.ts`) in place of `taskToMarkdown()`.
- **Undo for delete** — deleting a task (or a bulk-selected batch, see below) doesn't touch the database right away: it (and its subtasks) are hidden from every view immediately, and a "`<n> task(s) deleted`" toast with an **Undo** button appears for 5 seconds. Only once that window elapses uncancelled does it actually move to Trash (see below) — not a real `DELETE` anymore, see Trash for why. Undo just cancels the pending timer; deleting again while one delete is already pending commits the first one immediately rather than juggling two undo windows at once.
- **Trash** — a longer-retention safety net *beyond* the 5-second Undo above: once that window elapses, a deleted task now gets a `deleted_at` timestamp (a soft delete) instead of a real `DELETE`, and lands in a new "Trash" tab — day-grouped like Archive/History — where it can be browsed and **Restore**d, or finished off immediately with **Delete forever**. Restoring or trashing a parent cascades to its whole subtree together, mirroring how cascading delete already worked. Anything left in Trash longer than the configured retention is purged for good (`purgeExpiredTrash`, a plain string comparison against a date-only cutoff — `deleted_at`'s "date time" format sorts the same as it compares chronologically), checked once whenever the app starts rather than on a running timer, since a local app only needs to catch up on retention when it's actually opened. Trash is deliberately more minimal than Archive — just Restore/Delete forever, no Duplicate/Pin/Save-as-template — since none of those make sense on a task that's about to be purged. An "Empty Trash" button above the list purges everything in Trash immediately (after a `window.confirm`, same as any other irreversible action in the app) rather than waiting out the retention window — `emptyTrash()` shares its actual row-deletion logic with `purgeExpiredTrash()` (a small `deleteTrashedTaskIds()` helper both call), just without the date-cutoff `WHERE` clause.
- **Configurable Trash retention** — a "Trash retention" dropdown in the sidebar's Config panel (7/14/30/60/90 days, default 30, persisted the same `localStorage` way as theme/week-start/panel widths) replaces what used to be a hardcoded 30-day constant passed to `purgeExpiredTrash`. The purge itself still only runs once per app launch (not on a timer, not reactively the moment the dropdown changes) — changing the setting mid-session takes effect starting the *next* time the app opens rather than immediately sweeping through Trash, since silently deleting a batch of tasks the instant you turn a number down would be a surprising side effect of just changing a setting.
- **Undo/redo for edits** — a separate ↶/↷ pair in the header (and `Ctrl`/`⌘`+`Z` / `Ctrl`/`⌘`+`Shift`+`Z`) covers everything the task detail modal's Save button can change at once — title, description, due date/time, priority, repeat rule, reminder, and highlight color — as one combined history entry per Save click, since that's the single action the user actually took. Undoing reverts every one of those fields back to its value from just before that Save; redoing reapplies them. Making a fresh edit after undoing clears whatever was in the redo stack, same as any standard undo/redo. This is deliberately a separate mechanism from Undo for delete above (a pre-commit cancel window) rather than a unified system — the two undo concepts work differently enough (revert-after-commit vs. cancel-before-commit) that combining them would've meant compromising one to fit the other.
- **Per-task highlight color** — a `<input type="color">` picker in the task detail modal (new `highlight_color` column on `tasks`, nullable) tints just that row with a subtle alpha-blended wash of the picked color (via the same `hexToRgba` helper the custom accent picker uses, now shared from `lib/color.ts`), applied everywhere the row renders (main row, its tag strip, its description line). It's a purely personal marker, completely independent of tags and priority — no filtering, grouping, or other logic reads it. "✕" clears it back to no tint.
- **Add Task modal** — the main screen now just has a compact "+ Add task" button (or press `n`) instead of an always-visible form; clicking it opens a modal styled like the task detail view where title, description, due date/time, priority, and repeat are all entered at once, then closed again — no more permanently-visible priority/repeat controls cluttering every view. Description is a plain textarea here (no live markdown preview, unlike the full task detail panel) — that's the tradeoff for keeping a "quick capture" modal compact; open the task afterward if you want to fine-tune formatting. `createTask()` grew a matching optional `description` parameter (one INSERT instead of an INSERT-then-UPDATE) rather than the modal creating the task blank and immediately following up with a separate description write. "Cancel" (or clicking outside, or closing without submitting) discards the in-progress task entirely rather than partially saving anything. The quick inline "+ Subtask" add on a task row is unchanged by this — it's still the simple title-only field, since a subtask usually just needs a name.
- **Saved views** — a "+ Save current filters" link appears next to the tag/priority filters whenever at least one is active (or a search is typed), prompting for a name and storing that tag + priority + search combo as its own pill in a "Saved views:" row. Clicking a saved view applies its combo in one click (clicking it again clears back to no filters); a small ✕ on each pill deletes it. Deliberately only captures the tag/priority/search refinements, not which top-level view (All/Today/Calendar/etc.) is open, so a saved view is equally useful whether you're checking Today or All. Deleting a tag it references just drops that part of the combo (via `saved_views.tag_id` being nulled out) rather than breaking the saved view entirely.
- **Lists** — a "+ New list" button next to the built-in All/Today/Calendar/etc. views opens a small modal that just asks for a name. A list is its own independent grouping (`tasks.list_id`, nullable) — unlike the tag/priority/search filters, it's not a filter shortcut over the everyday task list: opening one shows the list's own name as the page title instead of "All", hides the tag/priority filter chips, "Saved views" row, and the active-filter banner entirely (there's nothing to filter — you're just looking at that list), and a task can belong to it without carrying any tag at all. Tasks still show up everywhere else they normally would regardless of list membership — Today, This Week, Calendar, a plain "All" browse — with a small "📋 ListName" badge in their subtitle row whenever they're not already being viewed inside that same list, so a tagless, list-only task is never invisible or unexplained elsewhere. Adding a task (or a subtask, which copies its parent's list) while a list is open assigns it to that list immediately; the task detail modal also has a plain "List" dropdown to move a task in, out, or between lists at any time. Each list has its own ✕ to delete it (tasks in it just lose that assignment, they aren't deleted) and a small color dot for the same kind of per-tab accent override custom tabs always had. `custom_tabs.tag_id` still exists purely as a legacy column from when a tab was just a tag-filter shortcut — nothing reads it for membership anymore, and deleting a tag no longer takes a list down with it. That same color-dot popover also has a "Description" textarea (new nullable `custom_tabs.description` column) for general free-text info about the list itself — what it's for, conventions to follow, whatever's useful beyond just the task list — shown as a subtitle line right under the page title whenever that list is open. Unlike the color input, typing doesn't write to the database on every keystroke; the textarea keeps a local draft that commits whenever the popover actually closes — on blur, but also explicitly on every other way of closing it (clicking outside, toggling the color dot, right-clicking a different list) — rather than relying on blur alone, since React unmounting a still-focused textarea via a state update (as the click-outside handler does) doesn't reliably fire its `onBlur` first, which used to mean a click-away-without-touching-the-textarea silently discarded whatever was typed. The same popover also has a "Default tag" dropdown (new nullable `custom_tabs.default_tag_id` column, distinct from the legacy `tag_id` — this one has a real, current meaning) — set it and any *new* task added while that list is open gets that tag automatically, on top of the list assignment it already gets. That's deliberately not retroactive, so changing or clearing the default tag never silently re-tags anything; an "Apply to all tasks in this list" button (shown only once a default tag is actually set) is the explicit, on-demand way to stamp it onto every task already in the list, in one bulk `INSERT OR IGNORE INTO task_tags ... SELECT ... WHERE list_id = ?` rather than one round-trip per task. Each list also has its own small ⠿ drag handle for reordering the "Lists" section itself, using the same before/after-the-target splice logic (and the same accent-colored top/bottom drop indicator) as task reordering, persisted via the `custom_tabs.sort_order` column that already existed for this — just a distinct `"application/x-todo-list-id"` drag payload instead of tasks' `"text/plain"`, so a list id dragged over a task row (or vice versa) can never be misread as the wrong kind of id. The same settings popover also has an "Icon" section (new nullable `custom_tabs.icon` column) — a small curated grid of ~24 emoji to pick from (there's no native emoji-picker input to defer to, unlike the color dot's `<input type="color">`) plus a "Remove icon" link once one's set. The picked emoji shows next to the list's name in the sidebar, and replaces the previously-hardcoded 📋 in a task's "in this list" badge (`TaskListRef` now carries `icon` alongside `name`/`color`) whenever that list has one set — purely cosmetic, nothing reads it for logic.
- **Bulk select** — a "Select" button (next to "+ Add task", on any list view — not Calendar/History) puts every task row into selection mode with its own checkbox, and shows a small action bar: **Complete**, **Tag** (pick from a small popover to add a tag to every selected task), **Postpone** (a popover asking "by how many days," applied to whichever *selected* tasks are actually overdue — same eligibility as the single-task Postpone button: has a due date, isn't recurring, since Skip is the recurring equivalent — a selected task that doesn't qualify is just silently left alone rather than erroring), and **Delete** (routes through the same Undo-backed pending delete as a single delete, just with a "N tasks deleted" toast instead of one title). Selecting a parent task is enough to act on its whole subtree too — completing or deleting cascades to descendants exactly like it already does for a single task, so there's no need to individually tick subtasks as well.
- **Duplicate task** — a "Duplicate" button on every task row (everywhere a row is shown, including Calendar's day-detail and History) copies its title, description, due date/time, priority, and tags into a new task, along with its *entire* subtask subtree (each descendant re-parented under its own sibling's duplicate, so the copied hierarchy matches the original exactly). The duplicate always starts fresh — not completed, no completion timestamp — and deliberately doesn't carry over recurrence (so the copy and the original don't end up racing to spawn the same "next instance") or attachments (those are just file paths, so "duplicating" one would only point two tasks at the same file rather than making a real copy). It lands as a sibling of the original, positioned immediately next to it rather than jumping to the top of the list.
- **Task templates** — a "Save as template" button on every task row captures its title, priority, tags, and its whole subtask subtree as a static, named blueprint (a `task_templates` table storing that tree as one JSON blob, since — unlike real tasks — a template never needs to be filtered, sorted, or joined against, only read back whole). A "Templates ▾" button next to "+ Add task" lists every saved template; picking one stamps out a brand-new task (and its whole subtask tree, tags included) in one click, using whatever due date is currently pending for the add form — the same default a manually-added task on that view would get. Templates are completely independent of the task they were captured from: editing, retagging, or deleting the original never touches a template already saved from it.
- **Natural language due dates (and times)** — typing a phrase like "tomorrow", "next friday", "in 3 days", or "next week" anywhere in the Add Task modal's title field shows a small "📅 Due `<date>`" hint beneath it; submitting then strips that phrase out of the title and sets the due date to the resolved date automatically (unless a title were *only* that phrase, in which case the text is left alone so the task doesn't end up with a blank title). A bare weekday name (e.g. "friday") means the next occurrence including today itself; "next friday" always skips the nearest one and lands on the following week's. A time phrase alongside a date — "at 3pm", "at 15:30", "noon", "midnight" — is detected and applied too (never on its own, since a time only means something once there's a date to attach it to); a bare hour with no am/pm, like "at 3", guesses pm for 1–7 and am for 8–12/0 since that's the more common casual meaning. This only kicks in while no due date/time has been picked yet — picking either by hand always wins and the hint disappears.
- **"See also" links** — a "See also" section in the task detail modal, right below "Depends on," lets any two tasks be cross-referenced without either one blocking the other's completion — a new `task_related` table, deliberately separate from `task_dependencies`. Unlike a dependency, the link is symmetric: linking A to B always means B is also linked to A, so it's stored as one canonical row per pair (the smaller id always first) rather than two directional rows that could drift out of sync. Each linked task shows as a clickable title (completed ones struck through) that jumps straight to that task's own detail panel, and a ✕ removes just that one link; adding one is the same "pick from a dropdown of every other task, then Add" pattern as "Depends on." Like dependencies, links aren't carried over by Duplicate or Save-as-template.
- **Click-outside-to-close for popovers** — every small anchored popover in the app (Templates ▾, the bulk-select Tag ▾ and Postpone ▾ pickers, a task row's "⋯" kebab menu, and the sidebar's per-tab color picker/notification-settings/accent-color popovers) now closes itself the moment you click anywhere outside it, not just by re-clicking its own toggle button or picking an option. A new shared `useClickOutside()` hook (`lib/useClickOutside.ts`) attaches a single `mousedown` listener to `document` — only while that specific popover is open, so idle popovers cost nothing — and closes it if the click landed outside the wrapper element the hook was given; that wrapper always contains both the toggle button and the panel itself, so clicking the toggle to *open* it is never misread as an "outside" click. The one popover this deliberately excludes is the sidebar's keyboard-shortcuts info panel, since that one already opens/closes on hover rather than a click and has nothing to close on-outside-click *from*.

This was a pure restructuring — every existing feature/handler kept working exactly as before, just re-homed into the new layout; no new functionality was added.
- **"More" views dropdown** — the sidebar's built-in views are now split into two groups: All/Today/This Week/No due date/Calendar stay as permanent top-level buttons (the ones actually reached for constantly), while History/Stats/Archive/Backlog/Trash — reviewed far less often — are tucked behind a "More ▾" button below them instead of permanently taking up sidebar space. Opening one from the dropdown closes it immediately after (matching every other popover's click-outside-to-close behavior via the same shared `useClickOutside()` hook), and the "More" button itself shows the active view's own name in place of "More" and picks up the same accent highlight whenever one of its five views is the one currently open, so it's never ambiguous that something's selected in there even while collapsed. Purely a `Sidebar.tsx` presentational change — the `View` type, the filter pipeline, and the command palette's "Go to `<view>`" commands are all untouched, since none of them cared how the sidebar happens to group its buttons.

Undo/redo and the keyboard-shortcuts "i" popover moved to the top of the main column instead, next to the view title — they're used often enough, and relevant enough to whatever's currently on screen, that they earned a permanent, visible spot rather than being buried. Everything else (export/import, notification settings, week-start, theme, accent) collapsed into a single "Config ▾" button at the bottom of the sidebar: one flat panel listing all of them, rather than each control keeping its own separate expand/collapse toggle like before — clicking DND, changing the snooze interval, or picking a color all stay open in the same panel instead of being nested behind their own individual popovers. The sidebar footer is now one button instead of a whole row of controls.
- **Click-outside-to-save for the task detail panel** — clicking anywhere outside the detail panel now saves whatever's been edited and closes it, the same as clicking "Save" (same title-required guard, same batched call) — reusing the shared `useClickOutside()` hook, scoped to the panel's own root element so nothing inside it (including the full-screen attachment lightbox) is ever mistaken for "outside." `Escape` deliberately keeps its existing behavior instead — it just closes without saving, since nothing's written to the database until Save actually runs, so the two dismissal gestures now mean genuinely different things (commit vs. cancel) rather than both silently discarding. This also closed a latent race: `onClose` used to be a bare `setSelectedTask(null)`, which — since the new outside-click save is asynchronous — could otherwise land *after* the user had already clicked a different task open, incorrectly closing that one instead; it now only clears the selection if the task it was closing is still the one actually selected.
- **Fixed: switching tasks while the detail panel was open showed stale data** — clicking a different task while one was already open used to leave every field (title, description, due date, etc.) still showing the *previous* task's values, and Save would then write that stale data onto the newly-clicked task instead of the one actually being viewed. Root cause: `TaskDetailModal` had no `key` prop, so React reused the same component instance across different tasks and only patched its `task` prop — every field is local `useState` seeded from `task`, which only runs on a component's *first* mount, so it never noticed the prop had changed underneath it. Adding `key={selectedTask.id}` makes React treat each different task as a genuinely new instance (a full unmount/remount) instead, so every field re-initializes fresh from the newly-selected task's actual data.

The native OS/browser right-click menu is suppressed (`e.preventDefault()`) in favor of this one. Opening it via the "⋯" button still anchors to the button as before; a `contextMenuPos` state (only set on right-click, reset on every other way of opening the menu) is what decides which positioning applies each time. Right-clicking anywhere on a list in the sidebar's "Lists" section does the same for that list's settings popover (color + description) — same `colorPickerTabId` state the color dot already toggles, just anchored at the cursor via its own `listMenuPos` instead of under the dot.

Fixed-position elements (the detail panel, every popover) are unaffected either way, since `overflow: hidden` on a non-transformed ancestor doesn't clip `position: fixed` descendants. This is a deliberate alternative to literal zoom-based scaling: making every panel width-adjustable and clipping rather than scrolling addresses "nothing should require scrolling to see" more robustly than shrinking text/UI to fit would.

It now anchors its right edge there instead, extending leftward and staying within the sidebar regardless of width. The right-click-opened version (anchored at the cursor rather than the dot) gets the same treatment via explicit clamping against `window.innerWidth`/`innerHeight` rather than a CSS anchor, since a cursor position has no "edge" of its own to anchor from.

- **Accessibility pass** — a screen-reader/keyboard review across every popover, modal, and drag-and-drop interaction in the app. Icon-only controls (⋯ kebab, ⠿ drag handles, ★/☆ pin, ○/◐ in-progress, ▶/⏸ timer, caret collapse toggles, every bare ✕) now carry an `aria-label` instead of relying on `title` alone — `title` is only used for an element's accessible *name* when it has no text content of its own, and an emoji/symbol glyph counts as content, so screen readers were literally announcing raw glyphs (or their Unicode names) instead of "Start timer"/"Pin to shortlist"/etc. Toggle buttons got `aria-pressed`/`aria-expanded` to match (pin, timer, in-progress, tag chips, priority/weekday chips, every popover-opening button), and every anchored popover/menu (task row's kebab menu, Sidebar's More/Config/list-settings panels, bulk-action Tag/Postpone pickers, Templates picker) now has a `role="menu"`/`role="dialog"` plus a label, instead of being an anonymous `<div>` a screen reader has no way to announce as a floating panel. The three real modals (Add Task, Manage Tags, Add List) and the Command Palette (a full `role="combobox"`/`listbox`/`option` treatment, with `aria-activedescendant` tracking the arrow-key-highlighted result) got `role="dialog"`/`aria-modal`; the non-modal slide-in detail panel got `role="dialog"` without `aria-modal`, matching that it doesn't block interacting with the rest of the app. Drag-and-drop (task reordering/reparenting, list reordering, both resize handles) had no keyboard equivalent at all before this — a mouse-only interaction is a hard accessibility failure, not just a rough edge. Alt+↑/Alt+↓ on a focused task row or list-name button now swaps it with its immediate sibling (reusing the exact same `handleReorder`/`handleReorderCustomTab` splice logic dragging already used, via a new `handleMoveTask`/`handleMoveList` that just figures out which neighbor to target), and both resize handles are now a real `role="separator"` with `aria-valuenow`/`min`/`max` and ←/→ keyboard support instead of a mouse-only `onMouseDown` div. The existing global `:focus-visible` outline (already in `index.css` from earlier in the project) meant keyboard focus itself was already visible everywhere — this pass was specifically about *what* gets announced once something has focus, and giving every drag-only interaction a non-mouse alternative.

Installed `vitest@^3.2.7` specifically (not the newest 4.x) since that's the last major aligned with this project's Vite 5, rather than also forcing a Vite upgrade just to add tests. `lib/duration.test.ts` is a minimal smoke test (four cases for `formatDuration`) proving the setup itself works end to end. Expected values for anything date-arithmetic-heavy (weekday-matching, month-rollover, recurrence previews, streak edge cases) were independently computed via one-off Node scripts *before* being hard-coded into the tests — the same verification habit used throughout development, just aimed at populating permanent assertions instead of a throwaway console.log this time. Notably covers the trickier edge cases already reasoned through during development: `computeStreaks`' "today doesn't break an in-progress streak, yesterday does" rule, `previewOccurrences`' occurrence-cap-counts-the-anchor off-by-one, `addInterval`'s Jan-31-plus-a-month rollover, and `nextReminderAfter`'s multi-day backlog catch-up.
- **`useReminders` hook** — the standalone-reminders background-poll effect (check every 60s, notify, then either mark a one-shot reminder as sent or roll a repeating one forward) was pulled out of `App.tsx` into `lib/useReminders.ts`, alongside the project's other custom hook (`useClickOutside`). A pure mechanical extraction, not a rewrite — same logic, same dependency array (`[tasks, dndEnabled]`, deliberately still excluding `reload` to match both the pre-extraction effect and its sibling `checkOverdue` effect that stays in `App.tsx`, neither of which re-subscribes on every render just because `reload`'s function reference changes each time). The 60-second interval constant (`OVERDUE_CHECK_INTERVAL_MS`) moved to `lib/appConstants.ts` since it's shared by both this hook and `checkOverdue`, rather than staying a private constant only one of the two former neighbors could still see. `App.tsx` shrinks by about 40 lines; the other two `App.tsx` extraction TODOs (keyboard shortcuts, tag/priority/search filtering) are separate, not-yet-started items — this was deliberately scoped to just the one self-contained effect rather than attempting the whole file at once.
- **`useKeyboardShortcuts` hook** — both keyboard-shortcut effects (the in-app `n`/`/`/arrows/Escape/undo/redo/command-palette `window` keydown listener, and the Ctrl/⌘+Shift+N OS-level global shortcut registration) moved from `App.tsx` into `lib/useKeyboardShortcuts.ts`, another pure mechanical extraction — identical handler bodies, identical dependency arrays. This one touches far more of `App.tsx`'s state than `useReminders` did (the in-app listener alone reads four modal-open booleans, `searchQuery`, `sortBy`, `tasks`, `undoStack`, and `redoStack`, plus calls five setters and three handler functions), so rather than a handful of positional parameters it takes one options object — the established multi-input-hook shape elsewhere would've meant a 15-argument function call, which is more error-prone (easy to swap two same-typed positional args) than one object literal with named fields. `undoStack`/`redoStack` are typed as `unknown[]` in the hook's params rather than importing `App.tsx`'s local `EditHistoryEntry` type — they're only ever there to trigger a fresh subscription when undo/redo history changes (the handler calls `handleUndo`/`handleRedo`, both unmemoized closures that need a live dependency to refresh against), never actually read inside the hook, so declaring their real element type would be a needless coupling. `SortOption` (previously `App.tsx`-local) moved to `lib/appConstants.ts` for the same reason `View`/`Theme` already lived there — so a hook could type against it without importing from `App.tsx` itself, which stays the top of this app's import graph, not something anything else imports from. `App.tsx` shrinks by roughly 135 more lines on top of the `useReminders` extraction.
- **`useTaskFilters` hook** — the tag/priority/search/list filter pipeline (`filterByTagPriorityAndSearch`, shared by the main non-archived list, Archive, and Trash) moved from `App.tsx` into `lib/useTaskFilters.ts`. Kept the `use` prefix anyway to match the name this was tracked under, even though strictly speaking it could be called conditionally without breaking the rules of hooks. Takes the criteria (`activeListId`/`activeTagFilter`/`priorityFilter`/`searchQuery`) as one `TaskFilterCriteria` object built once in `App.tsx` and reused across all three call sites, rather than four separate parameters repeated three times. Being a genuinely pure function (not just React-adjacent) made it a natural candidate for real unit tests too — `lib/useTaskFilters.test.ts` covers each filter stage individually plus the full four-way chain together, including the non-obvious detail that the priority filter's own descendant-inclusion runs against whatever the list/tag filters already narrowed the pool down to, not the original unfiltered task list. `App.tsx` shrinks by another ~35 lines; the `useReminders`/`useKeyboardShortcuts`/`useTaskFilters` trio completes every hook extraction that had been tracked as a TODO.
- **ESLint** — a baseline flat config (`eslint.config.js`, ESLint 10 + `typescript-eslint`'s plain non-type-checked `recommended` preset) with `npm run lint`. Deliberately minimal on the React Hooks side too: just the two classic rules (`react-hooks/rules-of-hooks` as an error, `react-hooks/exhaustive-deps` as a warning) rather than `eslint-plugin-react-hooks` v7's full "recommended" bundle, which now also pulls in a dozen React Compiler-oriented rules (purity, immutability, static-components, etc.) this codebase was never written against — a reasonable future step, not something to take on sight-unseen as part of a first pass. Running it cold against the existing codebase turned up 34 errors and 8 warnings, all now resolved one way or another rather than left as a messy starting baseline: two were genuine (a dead `let granted` reassignment in the notification-permission effect that was never read afterward, simplified away; a `cond ? a() : b()` used as its own statement in `TaskRow.tsx`, which is the codebase's own established shorthand elsewhere — resolved by configuring `no-unused-expressions` with `allowTernary`/`allowShortCircuit` rather than rewriting it into a less consistent `if`/`else`). The 30 `no-explicit-any` errors were all `lib/db.ts`'s row-mapper functions and raw `db.select<any[]>` calls — the standard, accepted boundary for `any` in a typed codebase (an untyped SQLite row on one side, the app's real domain types on the other) — so that file gets a scoped rule override instead of 30 speculative one-off row-shape interfaces nothing else would use. The 8 `exhaustive-deps` warnings were each individually checked against what they actually do before deciding anything — every one turned out to be a deliberate, already-reasoned-through omission (several already had explanatory comments predating this lint pass) rather than a real stale-closure bug: `App.tsx`'s trash-purge effect (empty deps on purpose, see Configurable Trash retention above), `Sidebar.tsx`'s description-draft resync (adding `customTabs` would clobber an in-progress draft on unrelated edits within the same popover), `TaskDetailModal.tsx`'s two dependency/related-candidate effects (the candidate arrays are freshly recomputed every render, so depending on them directly would run the effect on every render instead of only on genuine relationship changes), `TaskRow.tsx`'s collapse-signal effect (keyed on `collapseSignal?.version` specifically so repeated "Collapse all" clicks each still re-apply), and `useKeyboardShortcuts`'/`useReminders`' own effects (documented during their extraction earlier). Each got a scoped `eslint-disable-next-line` with a comment explaining why, rather than a blanket rule downgrade — so the exception is visible right where it applies instead of silently weakening the rule everywhere.
- **Shared style constants** — a new `lib/sharedStyles.ts` exports four base `CSSProperties` objects (`CARD_STYLE`, `MODAL_STYLE`, `POPOVER_STYLE`, `MENU_ITEM_STYLE`) factored out of ~30 near-identical inline style objects that had been copy-pasted across 13 files — every static list/day-group/stat-card container, every centered dialog (Add Task, Add List, Manage Tags, Command Palette), every anchored dropdown/settings popover, and the recurring "plain text button, full width, no border" menu-item shape (`TaskRow.tsx`'s own local `menuItemStyle` becomes an alias-free user of the shared one; `Sidebar.tsx`'s "More views" buttons pick it up for the first time). Each call site spreads the relevant constant and layers only its own genuinely different properties on top (position/anchor for popovers, `maxWidth` for modals, an occasional colored border like the Overdue section's), rather than repeating all four-to-eight shared properties by hand — so a future change to the app's card/popover look (say, a different shadow) now happens in one place instead of needing a find-and-replace across a dozen files. `TaskDetailModal.tsx`'s slide-in side panel deliberately keeps its own inline style instead of forcing a fit — it's genuinely a different shape (`borderLeft` only, no `borderRadius`, since it's flush against the window's right edge), not more of the same duplication. Net effect: ~250 lines removed across 13 files, and the production bundle shrank by about 4KB purely from the reduced duplication.
- **`App.tsx`'s view lookup** — the six-branch `view === "calendar" ? <CalendarView/> : view === "history" ? <HistoryView/> : ...` ternary chain became a flat `viewComponents: Partial<Record<View, ReactNode>>` object, looked up as `viewComponents[view] ?? (<>...fallback...</>)`. The five views without their own dedicated component (All/Today/This Week/No due date/My Day) still share one inline fallback fragment rather than being forced into the map — they don't share a single `view` key to hang an entry off, so five duplicate map entries pointing at the same JSX would've been *more* repetition, not less. Building all six `<XView/>` elements up front is safe despite only one ever actually being used: JSX is just a `React.createElement(...)` descriptor object until React reconciles it, so the other five never run their component bodies or touch the DOM — there's no six-views'-worth-of-hidden-rendering cost being paid here. A pure structural reorganization (same props, same components, same fallback content moved verbatim) rather than a line-count reduction, so `App.tsx` comes out slightly longer, not shorter — the win is that adding a seventh dedicated-component view going forward is one map entry instead of another `: view === "x" ? (...) :` link in a growing chain.
